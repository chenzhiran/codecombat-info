1　为什么需要哈希

Why Hashing

1.1 用列表一个个找

先比较两种"找东西"的办法：

用列表找：一个个看过去 C++ 
vector<string> names = {"安雅", "塔林", "艾达", "塞尼克"};     // 实际有一万个人

string target = "塞尼克";
for (int i = 0; i < names.size(); i++) {
    if (names[i] == target) {      // 从头一个个比
        cout << "找到了，第 " << i << " 个" << endl;
        break;
    }
}
// 最坏情况要比一万次 —— O(n)
问题　数据越多，找得越慢
用unordered_map找：算一下位置，直接去拿 C++ 
unordered_map<string, int> info = {{"安雅", 80}, {"塔林", 100},
                                   {"艾达", 60}, {"塞尼克", 95}};

cout << info["塞尼克"] << endl;       // 一次就拿到 —— 平均 O(1)
// 不管里面存了 10 个人还是 100 万人，花的时间几乎一样
关键　它不是"找"出来的，而是"算"出来的

1.2 哈希表的核心思想

哈希表的核心思想： 不用"一个个比"，而是用一个函数把"键"算成一个数字，直接跳到对应的位置去取。
· 列表像一排没编号的书，找书得一本本翻；
· 哈希表像带索引的图书馆，报书名就能直接走到那排书架。
所以它的查找速度是 O(1)——和数据量几乎无关。

2　哈希函数

Hash Functions

2.1 哈希函数在做什么

自己写一个简单的哈希函数 C++ 
int hashFunc(string key, int capacity) {
    int total = 0;
    for (char ch : key) {
        total = total + (int)ch;     // 把每个字符转成数字累加
    }
    return total % capacity;         // 取余，保证落在 0 ~ capacity-1
}

cout << hashFunc("apple", 10) << endl;     // 某个 0~9 的数
cout << hashFunc("banana", 10) << endl;    // 另一个数
要点　ord() 把字符转成编码；% 把结果压进桶的范围

2.2 好哈希函数的两条标准

好哈希函数的两条标准：
① 算得快——每次查找都要算一次，太复杂就得不偿失；
② 分布均匀——尽量让不同的键落到不同的位置，避免挤在一起。
如果所有键都挤到同一个位置，哈希表就退化成链表了，查找又变回 O(n)。

3　冲突怎么办

Handling Collisions

3.1 冲突是必然的

两个不同的键算出同一个位置，就叫哈希冲突。这是无法完全避免的（因为桶的数量有限），只能处理。

处理方法做法特点
拉链法每个桶挂一个列表，冲突的键都放进去最常用，实现简单，C++ 的 unordered_map 用的思想与此类似
开放寻址位置被占了就往后找下一个空位省空间，但删除比较麻烦
再哈希换一个哈希函数重新算位置计算量更大

3.2 冲突多了会怎样

冲突多了会怎样？ 如果所有键都挤在同一个桶里，哈希表就退化成一个链表——查找又变成 O(n)，
白白浪费了哈希的好处。
所以桶的数量要选得合适（通常比元素个数多一些），让每个桶尽量只放一两个。

4　unordered_map 就是哈希表

unordered_map Is a Hash Table

4.1 你早就在用哈希表了

你早就在用哈希表了 C++ 
unordered_map<string, int> d;
d["apple"] = 3;                 // 底层：算出 "apple" 的哈希位置，把 3 放进去
cout << d["apple"] << endl;     // 底层：再算一次，直接跳到那个位置取出 3

// 速度对比（一万条数据）
// 线性查找：最坏 10000 次比较
// 哈希查找：约 1 次定位 + 极少量比较
cout << (d.count("apple") ? "有" : "没有") << endl;   // 也是 O(1)
重要　unordered_map的键必须是可哈希的：数字、字符串、元组可以，列表不行

4.2 三条实用结论

三条实用结论：
① unordered_map的查找、插入、删除平均都是 O(1)——这就是它快的秘密；
② 键必须不可变（数字/字符串/元组），因为哈希值一旦变了就找不到了；
③ 哈希容器不保证顺序（unordered_map 的遍历顺序和插入顺序无关，别依赖它做题）。
哈希表的三大经典用法 C++ 
// ① 计数
vector<string> words = {"a", "b", "a", "c", "a"};
unordered_map<string, int> cnt;
for (string w : words) {
    cnt[w] = cnt[w] + 1;         // 没有这个键时会自动建出来，初值是 0
}
for (auto& p : cnt) cout << p.first << "：" << p.second << " ";
cout << endl;                    // a：3  b：1  c：1

// ② 去重
set<string> uniq(words.begin(), words.end());

// ③ 快速判断"见过没有"
unordered_set<int> seen;
for (int x : {3, 1, 4, 1, 5}) {
    if (seen.count(x)) cout << "重复了：" << x << endl;
    seen.insert(x);
}
要点　计数、去重、判重——这三件事用哈希做最快

5　代码实战

Level Practice
关卡

散列的牦牛

进入关卡 →
故事：牦牛管理员手里有一本名册，每头牦牛对应一个"存放位置"。 你报出名字，他不算、不翻，直接走向那格。
你怎么知道它在哪儿？你问。
他晃了晃手里的册子：名字进来的时候，就已经算好位置了。

思路：写一个哈希函数，把名字变成格子编号，再报出它在哪一格。 这就是哈希表的全部核心动作。

重点示例：把名字算成位置编号 C++ 
int hashFunction(string key) {
    int total = 0;
    for (char ch : key) {
        total = total + (int)ch;     // 字符编码累加
    }
    return total % 135;              // 取余，压到 0 ~ 134
}

string key = "someName";
hero.say("它在第 " + to_string(hashFunction(key)) + " 号存储格");
要点　累加 + 取余 = 最简单的哈希函数；ord() 把字符变成数字
和本单元的关联： 这一关的代码干的事，正是 C++ 的 unordered_map 在底层偷偷做的事：
把键（名字）算成一个下标，然后直接把值存到那个位置。
区别只在于：标准库用的哈希函数更复杂、冲突处理更完善，所以你用不着操心。

6　常见陷阱

Common Pitfalls
扣哒鸭 · 调试官
哈希这块的坑，一半在"键能不能哈希"，一半在"以为它什么都能做"。四条，看完就清楚了。
1
用列表当unordered_map的键。
扣哒鸭：会报 TypeError: unhashable type: 'list'。
键必须不可变——列表能改，所以不能做键。
真要表达"一组键"，可以把列表转成元组再当键。
正确做法：键用数字、字符串或元组
2
以为哈希表也保证顺序。想按插入顺序取第 3 个元素。
扣哒鸭：哈希表的核心是"按键直接定位"，不是"按位置顺序访问"。
要按顺序访问，就用列表；别拿unordered_map当列表用。
正确认识：unordered_map按键取，列表按位置取——各司其职
3
不该用哈希却用了。比如求"最大值"。
扣哒鸭：哈希表的强项是"按键快速定位"。 求最大值还是得遍历一遍，用不着哈希。
选数据结构的标准永远是"这个操作我要做多少次"。
正确认识：按键查找用哈希；求最值、排序还是用列表
4
自己写哈希函数时忘了取余。
扣哒鸭：累加出来的数字可能很大， 必须 % 容量 把它压到 0 到容量-1 之间，否则会越界。
这一步和循环队列取余是同一个道理。
正确写法：return total % capacity

7　题目练习

Practice

第 1 题改编自 2026 年 9 月 · C++ 七级 第 9 题，其余为原创练习题。

改编自 2026 年 9 月 · C++ 七级 · 第 9 题单选题
关于哈希表，下列说法正确的是（　　）。
A.只要哈希函数选择合适，就可以完全避免冲突
B.在链地址法中，查找一个元素的时间复杂度一定为 O(1)
C.开放定址法发生冲突后，会在表内寻找下一个可用位置
D.哈希表的查找速度与表中元素个数无关
查看答案与详解
答案：C。开放定址法的做法就是"算出来的位置被占了，就按约定在表内继续往后找（线性探测、二次探测等）"。
A 错：键的数量往往远多于桶的数量，由抽屉原理可知冲突无法完全避免，好的哈希函数只是让冲突更均匀；
B 错："一定"太绝对。链地址法平均是 O(1)，但如果大量元素挤在同一条链上，查找会退化；
D 错：元素越多、装载因子越大，平均查找长度也会变长，装载因子超过阈值就要扩容。
顺带记：链地址法删除方便（摘链即可），开放定址法删除要打"墓碑标记"，不能直接置空。
对应小节3.2 冲突多了会怎样。
原创练习题单选题
哈希表查找速度快，主要原因是（　　）。
A.它把数据排好了序
B.它用哈希函数直接算出数据的位置
C.它的存储空间比别人大
D.它用了更快的编程语言
查看答案与详解
答案：B。哈希表不做"逐个比较"， 而是先把键算成一个下标，直接跳到那个位置，所以平均是 O(1)。
A 错：它并不需要排序；C 错：哈希表其实是用额外空间换时间，但"快"的原因不是空间大。
对应小节1 为什么需要哈希。
原创练习题单选题
哈希函数里最后一步通常要执行"取余"运算，目的是（　　）。
A.让计算更复杂，显得高级
B.把结果压缩到桶的合法下标范围内
C.去掉重复的键
D.保证结果不会冲突
查看答案与详解
答案：B。哈希函数的原始结果可能是一个很大的数， 而桶的数量是有限的（比如 100 个）——
取余就把它压到 0 到 99 之间，正好对应桶的下标。
D 错：取余恰恰是造成冲突的原因之一（两个不同的键可能余数相同）。
对应小节2 哈希函数。
原创练习题判断题
哈希冲突是完全可以避免的，只要哈希函数写得足够好。（　　）
查看答案与详解
答案：错误（×）。桶的数量有限，而可能的键几乎无限多， 根据"抽屉原理"，冲突是无法完全避免的。
我们能做的只是"减少冲突"（好哈希函数）和"处理冲突"（拉链法、开放寻址）。
对应小节3 冲突怎么办。
原创练习题单选题
拉链法处理冲突的做法是（　　）。
A.把冲突的元素丢掉
B.把哈希值相同的元素串成一个列表，挂在同一个桶后面
C.重新分配一块更大的内存
D.把元素放到最后一个空桶里
查看答案与详解
答案：B。拉链法让每个桶挂一条"链"， 哈希值相同的键依次挂在后面。
查找时先定位桶，再在这条短链里逐个比较。
D 项描述的是"线性探测"（开放寻址的一种）。
对应小节3 冲突怎么办。
原创练习题判断题
C++ 的 unordered_map 底层是用哈希表实现的，所以它的键必须能算出哈希值。（　　）
查看答案与详解
答案：正确（√）。整数、字符串等基本类型可以直接做 unordered_map 的键； 没提供哈希函数的自定义类型不能直接做键。
原因很简单：键一变，哈希值就变了，原来存的位置也就找不到了。

原创练习题单选题
下列 C++ 代码执行后，输出的结果是（　　）。
1  unordered_map<string, int> d;
2  vector<string> words = {"a", "b", "a", "c", "a"};
3  for (string w : words)
4      d[w] = d[w] + 1;
5  cout << d["a"] << endl;
A.1　　B.2　　C.3　　D.报错
查看答案与详解
答案：C。"a" 在列表里出现了 3 次， 所以计数器的值是 3。
这是哈希表最经典的用法：用unordered_map做计数器，一遍遍历就能统计完。

原创练习题编程题
题目要求：一行文字里有若干单词，请找出第一个出现两次的单词；若没有重复则输出"无重复"。
查看参考答案与要点 
string text = "apple banana cherry banana apple date";
stringstream ss(text);
string w;
vector<string> words;
while (ss >> w) words.push_back(w);      // 按空格切词

unordered_set<string> seen;             // 用集合记录"见过的单词"
string answer = "无重复";

for (string& s : words) {
    if (seen.count(s)) {                 // 见过 → 它就是第一个重复的
        answer = s;
        break;
    }
    seen.insert(s);                      // 没见过 → 记下来
}

cout << answer << endl;                  // banana

输出：banana
要点：
① set 和 dict 一样是哈希实现的， in 判断平均 O(1)；
② 一边遍历一边往集合里加，第一个"已经在集合里"的单词就是答案；
③ 如果换成列表存"见过的词"，in 就要 O(n)， 整体会退化成 O(n²)——这就是哈希表的价值。
对应小节4 unordered_map 就是哈希表。

塞尼克 · 沙海向导
七级到这里就收官了。最后三句话：
一、哈希表用"算位置"代替"逐个找"，所以平均 O(1)。
二、哈希函数要算得快、分布均匀；末尾那个取余不能少。
三、冲突无法避免，常用拉链法把冲突的键串成链。
从雷鸣高塔出去，前面是寂灭王座——最后一站，也是最难的一站。

你在索引库里收获了什么

  • 哈希表——用哈希函数把键算成下标，直接定位，平均查找 O(1)。
  • 哈希函数——把任意键映射成固定范围的下标；要求算得快、分布均匀。
  • 取余的作用——把结果压到 0 到"容量-1"之间。
  • 哈希冲突——不同的键算出同一下标；无法完全避免。
  • 拉链法——冲突的键串成一条链，挂在同一个桶后面。
  • 退化风险——冲突太多时会退化成链表，查找变成 O(n)。
  • C++ 的 unordered_map——底层就是哈希表；键要能被哈希（整数、字符串等基本类型都自带）。
  • 三大用法——计数、去重、快速判重。
